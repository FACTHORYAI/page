# What our MSIs must satisfy for the Microsoft Store

Draft for W9, 2026-10-25. Applies to Facthory Page, Grid and Deck alike unless a row says otherwise.

**What was read.** The upstream WiX sources and scripts in each checkout (`packaging/windows/wordcraft.wxs`, `gridcraft.wxs`, `deckcraft.wxs`, `package.ps1`, `sign.ps1`), the brand patch sets (`facthory/brand.toml`, which renames, re-publishes and re-keys them at build time) and Page's release workflow (`.github/workflows/facthory-release.yml`, `facthory/release.py`). The wxs files still say WordCraft, GridCraft, DeckCraft and "Learning Machines LLC"; `rebrand.py apply` turns those into Facthory Page/Grid/Deck and "Bandpey GmbH", and gives each app its own UpgradeCode and component GUIDs from our namespace, before every build. Nothing here was built or run: a Windows test is still owed (last section).

## The rules

| Source | Rule |
| ------ | ---- |
| Store Policy 10.2.9 ([7.20](https://learn.microsoft.com/en-us/windows/apps/publish/store-policies)) | `.msi` or `.exe` only; the binary **and all of its PE files** signed with a certificate that chains to a CA in the Microsoft Trusted Root Program; a **versioned download URL** whose binary **must not change** after submission; a new versioned URL for every update; "Initiating the install must not display an installation user interface (i.e., silent install is required), however a User Account Control (UAC) dialog is allowed"; a standalone installer, not a downloader stub; PC only |
| Policy 10.2.3 | No offer to install secondary software not developed by you |
| Policy 10.2.7 | Users must be able to "cleanly uninstall and remove your product" |
| Policy 10.2.8 | Supported methods and user consent to change Windows settings or defaults |
| Policy 10.4.1, 10.4.2, 10.4.4 | Detect unsupported devices with a message; start promptly, stay responsive, never close unexpectedly; reasonable download time and installation success rate |
| [Upload app packages](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msi/upload-app-packages) | HTTPS URL on your own host; architecture per package (x86, x64, arm, arm64, neutral); "For MSI apps, the Store uses the default silent switch '/qn'"; the Store keeps copies of the latest packages and, if the hosted file is swapped, downloads the new one and re-certifies it |
| [Certification process](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msi/app-certification-process) | Malware scan; silent-install test: installs "without any user interfaces visible", "can be successfully installed when logged in with a standard user account", makes a Start menu and Programs entry, exposes ProductName, Publisher, Default Language and Version in Add/Remove Programs, and "can uninstall cleanly without leaving remnants of files, folder, and registry entries"; offline-installer test; bundleware check; driver/NT-service check. Up to three business days |
| [App package requirements](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msi/app-package-requirements) | Version numbering is the installer's business ("Package version numbering for Win32 is not supported through the Store") |
| [Update your MSI app](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msi/publish-update-to-your-app-on-store) | "The Store allows existing users to install in-app updates through your app, if your installer supports it. The Store does not provide these updates automatically or manually to existing users." The [Win32 distribution guide](https://learn.microsoft.com/en-us/windows/apps/distribute-through-store/how-to-distribute-your-win32-app-through-microsoft-store) adds: "The application is responsible for managing its own auto-updates" |

Insider-era reports (Store 22411.1401, Windows Insider build 27758, December 2024) describe a "provided and updated" badge for such apps and a user-initiated Update button that runs the publisher's newer installer ([Winaero](https://winaero.com/windows-11-build-27758-canary-updates-store-adds-several-fixes), [TheTechOutlook](https://www.thetechoutlook.com/new-release/software-apps/windows-insiders-now-will-be-able-to-update-win32-apps-directly-from-microsoft-store/)). The Learn pages above, updated in 2026, still say the Store does not update existing users, so plan as if it does not, and make sure our MSI behaves well if the Store does run a newer one over an installed copy (it does: see "Upgrade").

## Requirement by requirement

| # | Requirement | Our MSI today (after the brand build) | Verdict | Action |
| - | ----------- | ------------------------------------- | ------- | ------ |
| 1 | `.msi`, standalone, offline | WiX v5, `MediaTemplate EmbedCab="yes"`: the binaries are inside the MSI. No bootstrapper, no downloads during setup. The C runtime is linked statically (`+crt-static`, `package.ps1`), so there is no VC++ redistributable prerequisite | Meets | — |
| 2 | Silent install under `/qn` | **Page** uses `WixUI_Minimal` (licence and finish pages) and a "Launch Facthory Page" checkbox; both are UI-sequence only and are skipped under `/qn`. **Grid** shows its own dialog only when `UILevel = 5` and defaults the desktop shortcut to off. **Deck** has no UI at all | Meets (by reading) | Test: `msiexec /i <msi> /qn /l*v install.log` on a clean VM; confirm no window appears and exit code is 0 |
| 3 | UAC allowed; installs for a **standard user** | Since the upstream catch-up (WordCraft v0.12.0, GridCraft v0.13.0, DeckCraft v0.12.0) all three are dual-purpose packages (`Scope="perUserOrMachine"`, registry under `HKMU`): a new installation goes to the current account (`Programs\Facthory\Facthory <App>`) without elevation, and the first setup page offers an installation for everyone, which asks for UAC. Silent machine updates pass `ALLUSERS=1`; a copy in the other context is refused (`packaging/windows/INSTALLATION.md`). Our updater follows the installer's record (`HKLM` or `HKCU` `Software\Facthory <App>\InstallDir`) | Meets (by reading) | Test on a clean VM: `msiexec /i <msi> /qn` as a standard user installs without a prompt, exit code 0 |
| 4 | Every PE file signed, chaining to the Trusted Root Program | `package.ps1` signs `facthory<app>.exe` and `facthory<app>-cli.exe` before WiX packs them, then signs the MSI; `sign.ps1` uses SHA-256 file and timestamp digests (`/fd SHA256 /td SHA256 /tr …`) and ends with `signtool verify /pa`. **Page's MSI also contains WiX's own custom-action DLL** (`Wix4UtilCA` for the "Launch" checkbox, and WixUI's dialog helpers); it is a PE file inside the MSI | Meets for our files; **verify** WiX's | Check every PE inside the built MSI: `msiexec /a <msi> /qn TARGETDIR=<dir>` extracts the files, and the Binary table can be exported with `wix msi decompile`; run `signtool verify /pa /all` on each. WiX's DLLs are expected to carry the WiX project's signature; if not, drop the Launch checkbox (Page) for all builds |
| 5 | Certificate accepted by the Store | Pipeline supports a `.pfx` (`WINDOWS_CERTIFICATE`) or Azure Trusted Signing (now **Azure Artifact Signing**). See `owner-checklist.md` step 4 for which to use | Depends on the identity | Artifact Signing's public root, "Microsoft Identity Verification Root Certificate Authority 2020", is listed as **Included** with the Code Signing EKU in the Trusted Root Program's CCADB report (downloaded 2026-10-25 from `ccadb.my.salesforce-sites.com/microsoft/IncludedCACertificateReportForMSFTCSV`), so it meets Policy 10.2.9 as written. Confirm with Partner Center's package pre-check on the first signed MSI |
| 6 | Timestamp | `/tr` RFC 3161 timestamp on every signature (`timestamp.digicert.com` for a `.pfx`, `timestamp.acs.microsoft.com` for Artifact Signing) | Meets | Required with Artifact Signing, whose certificates live three days ([FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq)) |
| 7 | Versioned, immutable URL | Release files are named `facthory<app>-<version>-windows-<arch>.msi` and attached to a draft GitHub release `v<version>`, published by a person (`facthory-release.yml`). The URL `https://github.com/FACTHORYAI/<app>/releases/download/v<version>/facthory<app>-<version>-windows-<arch>.msi` is versioned. GitHub release assets can be deleted and re-uploaded, so the URL is not immutable by itself | **Gap** | Turn on GitHub **immutable releases** for the three repositories ([GA 2025-10-28](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/)): once published, assets cannot be added, changed or deleted and the tag cannot move. GitHub's download URL redirects to `release-assets.githubusercontent.com`; run Partner Center's package pre-check on the first one, and if a redirect is refused, mirror the file to a versioned path on facthory.com |
| 8 | Architectures | x64 and ARM64 MSIs, each built with `wix build -arch`; `package.ps1` refuses a binary whose PE machine type does not match. (Upstream also builds x86; our release workflow does not) | Meets | One Partner Center package entry per architecture. Windows 10 on ARM cannot run x64 code, so the ARM64 package matters |
| 9 | Add/Remove Programs: ProductName, Publisher, Language, Version | `Package Name` = "Facthory Page" etc.; `Manufacturer` = "Bandpey GmbH"; `Language="1033"`; `Version` from `Cargo.toml` (pre-release suffix dropped, because MSI versions are numeric); `ARPPRODUCTICON` set; `ARPURLINFOABOUT` = `https://facthory.com/<app>`; `ARPURLUPDATEINFO` = `https://facthory.com/<app>`; `ARPHELPLINK` = the GitHub issues page | Meets; links need live pages | (a) `facthory.com/<app>` must be live before submission. (b) Point `ARPURLUPDATEINFO` at `https://github.com/FACTHORYAI/<app>/releases` until the website has a download page. (c) Optional: `ARPNOMODIFY=1` (one feature, so "Change" does nothing useful) and `ARPCONTACT` = "Bandpey GmbH". (d) Keep four names identical: MSI `Manufacturer`, the certificate's subject (Artifact Signing uses the validated legal name), the Partner Center publisher display name, and the DSA trader name: **Bandpey GmbH**. The Store's "provided and updated by" line shows the publisher display name |
| 10 | Start menu and Programs entry | One advertised Start menu shortcut per app; App Paths entry (Win+R `facthory<app>`); Grid's desktop shortcut only when chosen, never under `/qn` | Meets | — |
| 11 | Upgrade behaviour | `MajorUpgrade AllowSameVersionUpgrades="yes"` with a downgrade error; a fixed UpgradeCode per app derived from `https://facthory.com/<app>/windows-installer` (`brand.toml [guids]`), distinct from upstream's so a Facthory app never replaces or shares components with an installed upstream app; a new ProductCode every build (WiX default); `RemoveExistingProducts` at WiX's default (after `InstallValidate`, a full uninstall then install) | Meets | The same MSI serves the website, GitHub, the Store and the in-app updater, so any of them can upgrade an install from any other. Never change the UpgradeCodes |
| 12 | Downgrade attempt | If a user's copy was updated in-app to a newer version than the Store's submission and the user then presses Install in the Store, the MSI refuses with its downgrade message and exits with an error | **Risk** (install-failure rate, Policy 10.4.4) | Keep the Store's package URL close to the latest release (see "Updates" below), and test what the Store shows in this case |
| 13 | Files in use, reboots | Not handled explicitly. If the Store (or the updater) runs `/qn` while the app is open, Windows Installer may need to replace files in use; under `/qn` with no `/norestart`, an automatic restart is possible | **Verify** | Test: install version N, open the app with a document, run version N+1 with `/qn`. If a restart is scheduled or forced, add `<Property Id="REBOOT" Value="ReallySuppress" />` to the wxs and make the updater close the app first (and register the app for Restart Manager restart). ## Updates and cadence

Upstream releases every one to three days; each Store submission can take up to three business days to certify, and a new submission replaces the one in progress. Submit to the Store on a slower rhythm (for example weekly, or when a release fixes something serious): new Store customers get the submitted version, and the in-app updater moves every install, from any channel, to the latest release.
